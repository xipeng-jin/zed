# Codex app-server feature-parity matrix

Asset for wayfinder ticket #69 on map #65. This is the parity contract downstream tickets consume: every native-agent-only UI capability in Zed mapped to its `codex app-server` v2 counterpart, plus the external-agent capabilities the new in-process backend must keep.

Research date: 2026-07-31. Sources:

- Zed workspace: `/home/xjin/Projects/worktrees/zed/hearty-drum/zed`, branch `migration/native-agent-server`. Gating machinery: `crates/acp_thread/src/connection.rs` (capability sub-traits, `Option<Rc<dyn …>>` getters defaulting to `None`), plus concrete-type downcasts `as_native_connection` / `as_native_thread` (`crates/agent_ui/src/conversation_view/thread_view.rs:1186,1194`).
- Codex: pinned schema rev `rust-v0.146.0` = `e363b08c9175ac1cbe5893615dd2cb9ddf95043b` (same pin as the types-sourcing decision, #67). Wire names from `codex-rs/app-server-protocol/src/protocol/common.rs`; semantics verified against `codex-rs/app-server/src/` and `codex-rs/core/src/`.

Classifications:

- **direct** — a codex analog exists; wire it up, no user-visible behavior change worth calling out.
- **gap** — an analog exists but with a semantic difference the implementation must bridge or the UX must absorb; the gap is described and, where a decision remains, the owning ticket named.
- **hide** — no codex analog; the affordance is hidden for codex threads via capability gates (per the map's standing parity rule: no dead buttons, no shims).

### Per-row notes

**A1 — rewind (gap).** `thread/rollback` drops the last N *turns*; Zed rewinds to a specific user message. The client must map `ClientUserMessageId` → turn count from the end. The wire supports this cleanly: `turn/start.clientUserMessageId` is echoed back on `userMessage` items as `clientId`, so the backend can maintain the correspondence. Three real gaps: (i) rollback is **deprecated** upstream (`thread.rs:1071` doc comment) — it works at the pin, but the non-deprecated escape hatch is `thread/fork` with `beforeTurnId` if it disappears; (ii) rollback is **rejected while a turn is in progress** ("Cannot rollback while a turn is in progress") — Zed's rewind path must cancel/await the turn first (Zed already cancels before `restore_checkpoint`; the plain-edit path must do the same); (iii) rollback **never touches files** — "Clients are responsible for reverting these changes" — which matches Zed's split exactly: `AcpThread::rewind` already does client-side `action_log.reject_all_edits` + terminal cleanup, and file restore is A2.

**A2 — checkpoints (direct).** Checkpoint creation (`git_store.checkpoint` before each prompt, `acp_thread.rs:3683`) and restore (`restore_checkpoint` = cancel → rewind → git restore) are entirely client-side and agent-agnostic; they are gated today only by `client_id` + `truncate` presence. Implementing A1 unlocks checkpoints for free. Codex's rollback contract ("clients revert files") is precisely this division of labor.

**A3 — manual retry (hide).** No `turn/retry` on the wire (confirmed absent at the pin). Emulation (rollback 1 + re-send original input) violates the standing no-shims rule and inherits rollback's deprecation risk. Hide the retry button in error callouts for codex threads. Mitigations that remain: A4 (server auto-retries transient failures and tells us via `willRetry`), and the user can re-type. If upstream adds retry, revisit.

**A4 — auto-retry banner (direct).** The `error` notification carries `willRetry: bool` ("transient and the app-server process will automatically retry; will not interrupt a turn") — map `willRetry: true` onto the existing `AcpThreadEvent::Retry` / `RetryStatus` banner instead of a terminal error callout.

**A5/A6 — titles.** `thread/name/set` is exact (persists, works on stored rollouts, emits `thread/name/updated`; names normalized server-side, empty rejected). But there is **no automatic title generation** — the sole `thread/name/updated` emission site is the explicit set. Zed's LLM title generation depends on Zed's `summarization_model`, which codex threads don't have. Contract: keep manual rename (wired to `thread/name/set`), hide "Regenerate Title" and the generating-title UI, rely on Zed's existing provisional title (first ~20 chars) and codex's `Thread.preview` (first user message) for unnamed threads in history.

**A7 — model selector (direct).** `model/list` returns richer metadata than Zed native uses: `displayName`, `description`, per-model `supportedReasoningEfforts` (+ `defaultReasoningEffort`), `serviceTiers` (+ `defaultServiceTier`), `isDefault`, `hidden`, upgrade/deprecation info. Implement `AgentModelSelector` over it; apply selection via `thread/settings/update` (or sticky `turn/start` override — both emit `thread/settings/updated` when effective settings change). Favorites stay client-side (`AgentSettings::favorite_models`). Two wire obligations: preserve `supportedReasoningEfforts` array order (README mandates it), and honor `hidden` unless `includeHidden` is requested. Grouping: codex's list is flat (no provider groups) — render ungrouped or single-group.

**A8 — profiles (gap, owned by [Profiles and modes](https://github.com/xipeng-jin/zed/issues/72)).** Zed profiles select *toolsets*; codex's axes are execution policy: `approvalPolicy` (`untrusted` / `on-request` / `never` / experimental `granular` — note **no `on-failure`** in v2), structured `sandboxPolicy` (`readOnly` / `workspaceWrite` / `dangerFullAccess` / `externalSandbox`), named permission profiles (`permissionProfile/list`, XOR with inline sandboxPolicy), and `collaborationMode` presets (`collaborationMode/list`). The matrix's contract: the profile-selector *slot* is kept for codex threads but its vocabulary becomes codex's policy axes; the exact mapping (which axes surface, which selector) is #72's decision. Note: **there is no config-profile selection on the wire** (config.toml profiles are read-only provenance in `config/read`) — only permission profiles are selectable.

**A9 — skills (gap).** Codex has first-class skills: `skills/list` (per-cwd, with `SkillMetadata` incl. display interface + enabled flag, plus per-root error lists that map onto Zed's skill-warning banners) and a `skills/changed` notification for live reload. Invocation is turn input: `$<skill-name>` in the text plus a `{"type":"skill","name","path"}` input item. The gap: the skill *catalog* comes from codex's own discovery (its skill format, its roots via `skills/extraRoots/set`), not Zed's `agent_skills` scanner — so for codex threads the slash-completion and add-context menus list codex skills, and Zed-format skills do not apply. Wiring the two menus to a different source is mechanical; no separate ticket.

**A10 — thinking/effort (direct).** `effort: ReasoningEffort` (`none|minimal|low|medium|high|xhigh|max|ultra|custom`) is sticky per thread/turn; per-model valid efforts + default come from `model/list`. Zed's thinking on/off toggle maps to `effort: none` ↔ default. `summary: ReasoningSummary` (`auto|concise|detailed|none`) is also available if wanted.

**A11 — fast mode (gap).** Zed's boolean fast-mode toggle (with confirmation popover) is a zed.dev concept. Codex's analog is `serviceTier` — an enumerated per-model list (`{id, name, description}`) with a default, settable per thread (double-`Option`: `null` clears). Shape mismatch: boolean toggle vs. N-tier picker. Contract: hide the fast-mode button for codex threads; surface `serviceTier` selection instead, in the model selector footer or settings-adjacent UI (placement decided with #72's selector layout, since it shares the toolbar). Cost/quota framing of tiers is codex's (`description` strings), not Zed's.

**A12 — token usage (direct, richer).** `thread/tokenUsage/updated` gives `total` and `last` (per-turn) breakdowns: `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens`, `totalTokens`, plus `modelContextWindow` (nullable). This exceeds Zed native (which has no cached split). Map into `acp_thread::TokenUsage`; `used/max` ratio and the ≥0.85 warning stay client-computed. Minor gaps: no `maxOutputTokens` (Zed's `input_max_label` subtraction degrades to whole-window; acceptable), and usage is replayed on `thread/resume` (an improvement — restored threads show usage immediately). Per-turn output tokens for the turn label come from `last.outputTokens` directly instead of accumulation.

**A13 — compaction (direct).** `/compact` → `thread/compact/start` (fire-and-forget; progress streams as a normal turn). Timeline entry: the canonical signal is the `contextCompaction` **item** (the `thread/compacted` notification is deprecated and no longer emitted by the v2 server) → maps to `AcpThread::push_context_compaction`. Auto-compaction is server-side and config-driven (`model_auto_compact_token_limit`). There is **no "context low" signal** — irrelevant, since Zed's near-limit callout is already computed client-side from token usage; keep it, with the callout's action text unchanged. One behavioral note: compact turns are `TaskKind::Compact` and reject steering (see A14).

**A14 — steer (gap).** Semantics differ meaningfully. Zed-native "steer" ends the turn at the next tool boundary and then sends the queued message as a new turn. Codex `turn/steer` **injects input into the still-running turn** — generation is not aborted, the same `turnId` continues, input is consumed at the next model-request boundary. Codex's is the stronger primitive; the queue UI's "Steer" flag maps to sending `turn/steer { expectedTurnId }` instead of flag-then-wait. Implementation obligations: pass `expectedTurnId` (mismatch/`NoActiveTurn` errors mean the turn ended first — fall back to normal send); handle `ActiveTurnNotSteerable { turnKind: review|compact }` by queueing normally; note `turn/start` on a busy thread implicitly steers (server-side behavior), so the client should be deliberate about which it calls. "Send Now" (cancel + send) maps unchanged (`turn/interrupt` + `turn/start`).

**A15 — feedback (hide).** Zed's thumbs feedback posts thread data to Zed's cloud via the `telemetry()` capability, org-gated. Codex has no rating endpoint; `feedback/upload` is a whole-thread bug report to OpenAI with logs — different audience, different consent story. Return `None` from `telemetry()` → `/helpful`, `/not-helpful`, and thumbs buttons vanish via existing gates. Generic telemetry events (`Agent Message Sent` etc., keyed by `telemetry_id()`) still fire; they don't depend on the capability.

**A16 — sandbox indicator (gap, owned by [Profiles and modes](https://github.com/xipeng-jin/zed/issues/72)).** Zed's indicator attests *Zed's own* command sandboxing; codex commands run in *codex's* sandbox, whose effective policy is known (`thread/start` response `sandbox: SandboxPolicy`, updates via `thread/settings/updated`). The "verified" attestation machinery has no codex analog; hide it. Whether codex threads show a sandbox-mode status chip (read-only/workspace-write/full-access) is part of #72's mode-surface design.

**A17 — subagents (gap, graduated to its own ticket).** The protocol surface is now known: `collabAgentToolCall` items (spawn/sendInput/resume/wait/close, `receiverThreadIds`, per-agent status map), `subAgentActivity` items, `Thread.parentThreadId` / `agentNickname` / `agentRole`, and `thread/list` child filters (`parentThreadId` / `ancestorThreadId`). Zed's subagent UI is keyed on tool-call `subagent_session_info` meta plus `load_subagent_session`. The mapping decisions (which items become subagent tool calls, how child-thread streams are suppressed/surfaced, whether child threads are loadable as Zed subagent views) are a coherent ticket of their own — see [Sub-agent rendering](https://github.com/xipeng-jin/zed/issues/80).

**A18 — rules indicator (gap).** Codex loads AGENTS.md-style instructions itself and reports what it loaded: `thread/start` response `instructionSources: Vec<path>`. Zed native counts live per-worktree `.rules`. Contract: for codex threads the tooltip's "Rules" section lists/counts `instructionSources` (a start-time snapshot, not live-updating — acceptable); the global-AGENTS.md line is already client-side and stays.

**A19 — streaming-diff placeholder (direct).** Purely a client-side rendering gate (`as_native_connection`). Codex provides the needed signals: `fileChange` item arrives `inProgress` via `item/started`, patches stream via `item/fileChange/patchUpdated`. Extend the gate to codex connections. (Whether `turn/diff/updated` — the turn-cumulative unified diff — feeds Zed's action-log diffs is part of the streaming-rendering ticket, [Streaming rendering onto AcpThread](https://github.com/xipeng-jin/zed/issues/81).)

**A20 — model-not-available (gap).** No dedicated wire error: an invalid model surfaces as `BadRequest`/`HttpConnectionFailed{httpStatusCode}`. But the client holds the `model/list` catalog (with `hidden`, `upgrade`, deprecation info), so "configured model no longer offered" is detectable client-side at selector-build time — validate there and fall back to the `isDefault` model with a callout, rather than waiting for a turn failure. The zed.dev-specific "Configure Provider" actions don't apply; the degraded generic callout path (`thread_view.rs:10967`) is the base behavior.

**A21 — payment/upgrade (hide + replace).** Zed's payment-required, trial-end, and upgrade UI is zed.dev-plan-specific and already gated on the zed.dev provider — it naturally never renders for codex threads. Codex's own limit world (`UsageLimitExceeded`, `SessionBudgetExceeded`, `ServerOverloaded` error infos; `account/rateLimits/read` + sparse `account/rateLimits/updated` with used-percent windows, credits, plan type) is new surface owned by [Auth and account surface](https://github.com/xipeng-jin/zed/issues/73).

**A22 — history (direct, richer).** `thread/list` supports cwd filtering (matching Zed's per-project history), titles (`name`) + `preview` + created/updated/recency timestamps, pagination, full-text `thread/search`, archive/unarchive/delete (delete cascades to spawned descendants), and pinning. Implement `AgentSessionList` (with `supports_delete → true`) over it. Resume: `thread/resume` replays full turn history (unlike ACP resume which replays nothing) → `supports_load_session` can be true without the "resumed without history" notice. Details (which store is authoritative, ThreadMetadataStore interplay, `sourceKinds` filtering to exclude subagent/review threads) are owned by [Session persistence, resume, and history listing](https://github.com/xipeng-jin/zed/issues/74).

**A23/A24 — @thread mentions, export (hide in v1).** Both require reading full thread content through Zed-native stores. `thread/read` could feed either later; neither is worth a shim in v1.

## B. External-agent capabilities the codex backend must keep

The new backend implements `AgentConnection` directly (per the core-architecture decision on #66), so nothing from `AcpConnection` comes for free. What must be re-provided, and from what:

| # | Capability | Today (AcpConnection) | Codex backend source | Class |
|---|---|---|---|---|
| B1 | Login / auth | `auth_methods` + `authenticate` + `terminal_auth_task` (e.g. `claude /login` terminal) | `account/read` (`requiresOpenaiAuth`), `account/login/start` (ChatGPT OAuth `authUrl`, API key, device code), `account/login/completed`, `account/logout`, `account/updated` | **gap** → [Auth and account surface](https://github.com/xipeng-jin/zed/issues/73) |
| B2 | Session modes | `session_modes()` (ACP `session/set_mode`) | folded into A8's policy axes (approval/sandbox/collaborationMode) | **gap** → [Profiles and modes](https://github.com/xipeng-jin/zed/issues/72) |
| B3 | Config options (`session_config_options`) | generic dropdowns from the agent | superseded by first-class selectors (A7 model, A10 effort, A11 tier, B2 modes) | **superseded** — return `None` |
| B4 | Permission requests | `session/request_permission` → flat options | `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval` (richer: `AcceptForSession`, execpolicy/network amendments, `commandActions`, cancel-vs-decline distinction) | **gap** → [Approvals onto AcpThread permission model](https://github.com/xipeng-jin/zed/issues/71) |

**B1 note.** Codex login is URL-based (client opens `authUrl`; completion arrives as a notification), not terminal-based — `terminal_auth_task` is not needed; the auth-required state + method buttons UI (`render_auth_required_state`) is reused with codex methods. `Unauthorized` error info and `account/chatgptAuthTokens/refresh` (server→client) round out the surface; all owned by #73.

**B7 note.** This is the one genuinely new question the matrix surfaced: Zed today forwards project-configured MCP servers per-session; the app-server has no such parameter — MCP servers live in codex's own config. Whether Zed writes them through (`config/batchWrite` + reload), scopes them somehow, or simply doesn't forward project MCP servers to codex threads is now its own ticket.

## C. Codex surface with no existing Zed affordance (informational)

Not required for parity; listed so downstream tickets know it exists. Rate-limit/credits/plan display (`account/rateLimits/*`, `account/usage/read`) — #73. `model/rerouted` + `model/verification` notifications (backend silently rerouted the model; render informationally at most). Reasoning `summary` preference. Web-search / image-generation / image-view / sleep items (render as generic tool calls). Review mode, `fs/*`, realtime, plugins/marketplace, remote control — out of scope per the map.

## Contract summary

- **Direct (wire up):** rewind-adjacent checkpoints (A2), auto-retry banner (A4), set-title (A5), model selector (A7), effort (A10), token usage (A12), compaction (A13), diff placeholder (A19), history/list/resume (A22, B9), elicitations (B5), slash commands (B6), version (B11).
- **Gap (bridge, owner named):** rewind (A1), profiles→policy axes (A8, #72), skills source (A9), fast-mode→serviceTier (A11), steer semantics (A14), sandbox display (A16, #72), subagents (A17, #80), rules→instructionSources (A18), model-not-available detection (A20), auth (B1, #73), approvals (B4, #71), MCP strategy (B7, #82), terminal/streaming rendering (B8, #81), multi-root (B10).
- **Hide (capability-gate off):** manual retry (A3), title generation (A6), feedback (A15), sandbox attestation badge (A16), zed.dev payment/trial UI (A21), @thread mentions (A23), thread export (A24), data-retention flow (A25), plus `session_config_options` and ACP `UsageUpdate` superseded outright.
